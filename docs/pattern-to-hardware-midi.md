# From a pattern hit to hardware MIDI

This walkthrough follows the default BD1 row from a host timeline block to a
MIDI note. BD1 uses MIDI note 36, but that pitch is no longer attached to the
PatternPlayer or an engine route. It is resolved by a Voice parameter.

## 1. The fixed composition

`LivePatternSequencerProcessor` constructs these objects for BD1:

```text
PatternPlayer 0
    | hit                     Pitch ModulationPlayer 0 --+
    +-----------------------> Intensity Player 1 --------+--> Voice 0
    |                         Gate ModulationPlayer 2 ----+       |
    +------------------------------------------------------------> trigger
                                                                  |
                                               +------------------+------------------+
                                               |                                     |
                                        MIDI OutputBinding                    CV OutputBinding
```

All three modulation players advance from actual BD1 hits. Pitch selects a
one-step generic modulation representing 36/127 of the pitch range. Gate
selects a shared one-step half-gate modulation. Intensity selects the generic
shape shown in the row's Velocity editor.

The binding records, not the players, state what each signal means:

```text
ModulationPlayer 0 -> Voice 0 Pitch
ModulationPlayer 1 -> Voice 0 Intensity
ModulationPlayer 2 -> Voice 0 Gate
PatternPlayer 0    -> Voice 0 Trigger
Voice 0 Triggers   -> MIDI endpoint, route 0
Voice 0 Triggers   -> CV endpoint, route 0
```

## 2. The host supplies time

`processBlock()` reads the playhead and builds a half-open `TimelineBlock`:

```text
[ppqStart, ppqEnd)
ppqEnd = ppqStart + sampleCount * tempoBpm / (60 * sampleRate)
```

A start or seek marks a transport discontinuity. A continuing block is a
discontinuity only if its start differs from the previously expected end beyond
a small sample-derived tolerance.

Before graph processing, the processor attaches the current JUCE MIDI and audio
buffers to the registered renderers. The audio buffer is cleared because every
CV channel is generated by this plug-in.

## 3. PatternPlayer emits rhythm, not a note

On a clock boundary, PatternPlayer maps its playback position through the
inclusive window and offset. If the visible step is active, it emits:

```text
PatternHit {
    ppqPosition
    source PatternPlayerId
    hit TriggerId
    nominalStepLengthPpq
}
```

It also emits `PatternCycleBoundary` at the first position of every active
window, even when that position is a rest. Cycle signals drive external pattern
transitions and armed reset-to-master commands; they are never rendered.

BD1's PatternPlayer does not read a velocity shape, select note 36, calculate a
gate end, or know that MIDI and CV exist.

## 4. The hit establishes parameter values

The runtime graph propagates BD1's logical hit to all three ModulationPlayers.
Each advances once and emits an exact `NormalizedValue` at the same PPQ.

For the default constant velocity shape, the original 8-bit value 201 is stored
exactly through the normalized conversion. The four-step shape uses the values
255, 100, 225, and 150. These records are generic; “Velocity” is the meaning of
their current destination binding.

At the timestamp, the scheduler applies every modulation value before delivering
the hit to trigger bindings. Voice 0 therefore samples the newly advanced
values, not the preceding steps.

The Voice descriptors perform the mappings:

```text
Pitch:     normalized * 127 semitones
Intensity: normalized * 1
Gate:      normalized * triggering step duration
```

There are no implicit required defaults. If Pitch, Intensity, or Gate has not
received a value, Voice 0 drops the trigger and increments a bounded diagnostic.

## 5. Voice resolves the trigger

For a positive Gate value, Voice 0 creates a Voice-scoped Trigger ID and emits a
semantic start containing resolved pitch and intensity. It schedules the end at:

```text
endPpq = hitPpq + gateRatio * nominalStepLengthPpq
```

The minimum positive duration is one sample in PPQ. Gate zero produces no
audible resolved trigger. If another hit arrives while the Voice is active, the
old end is emitted before the replacement start.

The default BD1 constants resolve approximately to:

```text
pitch       = 36 semitones
gate ratio  = 0.5
intensity   = 201 / 255
```

The semantic result is protocol-neutral:

```text
triggerStart(Voice 0, Trigger N, pitch 36, intensity 201/255)
triggerEnd  (Voice 0, Trigger N)
```

## 6. Output policy runs after logical work

Mute and directed simultaneous-hit suppression are evaluated only when resolved
triggers are routed. A muted BD1 hit has already advanced its PatternPlayer,
three ModulationPlayers, command edges, and Voice state.

If a start is withheld, the graph remembers that decision for its Trigger ID.
Its later semantic end is withheld as well. This prevents an unmatched note-off
or CV gate release from affecting another audible trigger. Continuous Voice
parameter bindings are not muted by this policy.

## 7. Output bindings create routed events

The two BD1 trigger output bindings copy the semantic event into the MIDI and CV
endpoint batches. Each routed envelope contains:

```text
VoiceId 0
RouteId 0
validated frame offset
stable graph/binding order
resolved SequencerEvent
```

PPQ is converted to a sample frame with nearest-sample rounding:

```text
rawFrame = (eventPpq - blockPpqStart) / ppqPerSample
frame    = clamp(round(rawFrame), 0, sampleCount - 1)
```

Events outside the valid block tolerance fail the batch. At the same frame,
controls sort before ends and ends before starts, followed by stable binding
order.

## 8. MIDI rendering

`MidiBufferRenderer` rounds and clamps the resolved pitch to note 0 through 127.
It maps normalized intensity to the 1 through 127 concrete note-on range.

For intensity 201/255:

```text
round((201 / 255) * 127) = 100
```

The emitted message is therefore a note-on for channel 1, note 36, velocity 100
at the routed frame. Semantic intensity zero still becomes concrete velocity 1;
it is not encoded as the MIDI convention for note-off.

On a start, the renderer remembers the concrete note using Voice, Route, and
Trigger identity. On the matching end it emits note-off for that remembered
note. A pitch change after the start cannot release the wrong key.

## 9. CV rendering in parallel

The same Voice trigger reaches `CvBufferRenderer` through its independent output
binding. Route 0 owns three channels:

```text
channel 0: gate
channel 1: pitch voltage
channel 2: continuous control
```

The trigger start raises gate and updates pitch. The exact matching end lowers
the gate. Pitch, gate, and control state are filled across eventless blocks so
hardware outputs hold their values between events.

## 10. Stops, seeks, and failure

On a transport discontinuity the graph resets renderer trigger state before
processing the restarted logical sequence. On stop, graph processing resets
players and Voices and physical outputs are forced safe. MIDI emits all-notes-
off when a buffer is attached; CV gate, pitch, and control values return to zero.

Work-queue overflow, semantic-event overflow, invalid frame conversion, output-
batch overflow, or renderer failure also fails safe: the processor resets the
runtime and both physical endpoints rather than risking a lost release.
